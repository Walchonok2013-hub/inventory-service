# Менеджер домашних запасов (Inventory Service)

Тестовое задание: разработка backend-сервиса для управления домашними запасами продуктов и бытовых товаров.

## 📋 О проекте

Сервис позволяет пользователю вести учет товаров, партий, отслеживать сроки годности, прогнозировать расход и получать рекомендации.

**Ключевые особенности реализации:**
*   **Учет партий:** Один товар может иметь несколько партий с разными сроками годности и местами хранения.
*   **Конкурентный доступ:** Защита от двойного списания остатков через блокировки строк (`SELECT ... FOR UPDATE`).
*   **Идемпотентность:** Все мутирующие запросы поддерживают заголовок `Idempotency-Key`.
*   **Прогнозирование:** Расчет даты окончания товара на основе истории списаний.
*   **Автоматизация:** Фоновые задачи (Celery) для пересчета прогнозов, генерации уведомлений и обновления списка покупок.

## 🧠 Бизнес-логика и архитектурные решения

### Алгоритм списания (Consume)
При запросе на списание товара система использует стратегию, указанную в запросе:
1.  **`expires_first`**: Выбираются партии с ближайшим сроком годности. Списание идет последовательно, пока не будет набрано нужное количество.
2.  **`oldest_first`**: Выбираются самые старые партии (по дате покупки).
3.  **`manual`**: Пользователь явно указывает `batch_id`.

**Защита от ошибок:**
*   Если остатка недостаточно, возвращается ошибка `INSUFFICIENT_STOCK` с деталями.
*   Используется транзакция БД с блокировкой строк (`FOR UPDATE`), чтобы избежать состояния гонки при параллельных запросах.

### Идемпотентность
Все запросы, изменяющие состояние (создание партии, списание, корректировка), проверяют заголовок `Idempotency-Key`.
*   Если запрос с таким ключом уже был обработан, система возвращает результат первого выполнения без повторного изменения данных.
*   Реализация: проверка наличия ключа в специальной таблице или Redis перед началом транзакции.

### Прогнозирование расхода
Прогноз строится на основе среднего дневного расхода за последние N дней (по умолчанию 14 дней).
*   Формула: `Средний расход = Общее количество списанного / Количество дней с активностью`.
*   Если данных недостаточно (< 3 операций), прогноз не строится (`confidence: insufficient_data`).

### Фоновые задачи (Celery)
Запланированы следующие периодические задачи (запуск раз в сутки):
1.  **Пересчет прогнозов:** Обновление полей `estimated_days_remaining` для всех активных товаров.
2.  **Генерация уведомлений:** Поиск просроченных и истекающих товаров, создание записей в таблице `notifications`.
3.  **Обновление списка покупок:** Проверка товаров с низким остатком и добавление их в список покупок.
